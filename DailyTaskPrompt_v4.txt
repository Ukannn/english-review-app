====================
candidate_generation：按缺口补充个性化素材
====================

1. 读取 Config 并确认 contract_version=4.0；读取 Candidate Generation Inbox 的真实表头。正式表头为：
Request ID | Queue Date | Requested Count | Available Count | Shortfall Count | Position | Candidate | Chinese Cue | Candidate Type | Source | Context | Why Useful | Topic | Difficulty | Natural Example | Common Mistake | Generation Batch ID | Model ID | Generation Status | Created At | Committed At | Candidate ID | Contract Version

2. 如果提示词末尾有 EXPECTED_REQUEST_ID，只筛选该 Request ID；否则全表必须恰好存在一个有效请求元数据行：
- Position=0；
- Generation Status=requested；
- Contract Version=4.0；
- Request ID 非空且唯一；
- Queue Date 是真实日期；
- Shortfall Count=N，N 为 1–150 的整数；
- 如果提示词末尾有 EXPECTED_REQUEST_ID / EXPECTED_COUNT，必须分别等于 Request ID / N。
若没有请求，回复“当前没有待补充的素材缺口”；若多于一个，报告全部 Request ID 并停止。

3. 检查该 Request ID 是否已有一个完整 active Generation Batch。active 指 Generation Status=staged 的 Position>0 行：
- 若恰好 N 行、Position 恰好为 1–N、只有一个 Generation Batch ID 且字段合法，固定范围回读后复用，不重复写；
- 若出现多个 active Generation Batch ID 或不完整 active 批次，停止并报告歧义；
- 完全没有 active 行时才生成。

4. 为真正个性化生成素材，读取以下真实数据并只使用有界必要范围：
- Context Inbox / Context Candidate Inbox：用户亲自收集的真实语料、选中片段和已确认建议；
- Phrase Bank：已经学过的搭配、掌握阶段、下次复习、常见错误；
- Review Log / Error Log：实际答案、薄弱点、错误类型；
- Candidate Bank：现有候选、来源和状态，用于去重与理解用户兴趣；
- 当前对话上下文或用户账户可用记忆中的长期话题与现实需求（若当前模型可见）。

素材原则：
- 用户亲自收集并确认的素材由 Apps Script 排在最高优先级；本模式只补当前真实缺口，不覆盖、不降级、不重复用户素材；
- 生成内容要结合用户平时讨论的话题、已暴露的英语薄弱点，以及工作、沟通、日常生活中高频且可迁移的表达；
- 优先固定搭配、短语动词、介词结构、习惯表达、可复用句型和组合含义不能逐词推导的表达；
- 不生成普通孤立单词、专有名词、一次性术语、过长完整句子或过度生僻表达；
- Candidate 必须规范化为可复习 chunk，例如 steering customers toward → steer someone toward something；
- 与 Phrase Bank 的 Chunk/Canonical Pattern、Candidate Bank 的 Candidate、用户语料已确认建议及本批建议按标准化文本去重；
- 必须恰好生成 N 条通过上述检查的不同素材，不设置固定后备库存，不多生成。

5. 使用唯一 Generation Batch ID，例如 CGEN-<Request ID>-<yyyyMMddHHmmss>。向 Candidate Generation Inbox 一次性追加 N 行，每行严格 23 个 CellData，按正式表头顺序写入：
- Request ID、Queue Date、Requested Count、Available Count、Shortfall Count：从请求元数据行原样复制；
- Position：1–N；
- Candidate：规范化英文词块，非空；
- Chinese Cue：自然准确中文提示，非空；
- Candidate Type：固定 chunk；
- Source：写 ChatGPT personalized on-demand；
- Context：说明它与用户话题、薄弱点或生活高频需求的具体联系；
- Why Useful、Topic、Natural Example：非空；
- Difficulty：只能 easy、medium、hard；
- Common Mistake：可为空，但有典型错误时应填写；
- Generation Batch ID：本批唯一且一致；
- Model ID：写当前实际模型的可读名称；
- Generation Status：staged；
- Created At：当前真实 Asia/Shanghai 时间；
- Committed At、Candidate ID：留空；
- Contract Version：文本 4.0。

6. 固定范围回读确认：恰好 N 行、Position 1–N、一个 Generation Batch ID、Request/数量字段与元数据完全一致、必填字段非空、无标准化重复、状态全为 staged、Contract Version 全为文本 4.0。

7. 成功后回复：
“个性化素材已暂存。请返回答题网页，系统会去重、写入候选池并继续准备题组：YOUR_WEB_APP_URL”
不得宣称 Candidate Bank 已写入。

====================
question_prepare：按冻结 Queue 出题
====================

1. 读取 Config 并确认 contract_version=4.0；读取 Daily Queue 的真实表头及所有 Contract Version=4.0 的有界数据。不要自行推算“今天”选择题组。

2. 只按 active Queue 分组：Queue Status 全部为 planned，或全部为 presented。若存在 EXPECTED_QUEUE_ID，只筛选该 Queue ID；否则全表必须恰好存在一个满足全部条件的 active Queue：
- 同一个且唯一 Queue ID / Queue Date；
- Planned Count=N，N 为 1–150 的整数，所有行一致；旧行 Planned Count 为空时按 20；
- 恰好 N 行；
- Position 恰好为 1–N 且无重复；
- Adjusted Target=T，T 为 1–N 的整数且所有行一致；为空时 T=N；T 是本次实际生效题数，N 只表示该 Queue 已保留的最大题目集合；
- N 个身份唯一：旧词块用 Phrase ID，新词块用 Candidate ID；
- Queue Status 必须整组一致，只能 planned 或 presented；presented 时 Session ID 和 Presented At 必须分别全组一致且非空；
- Created At 均为真实时间戳，Asia/Shanghai 日期部分等于 Queue Date；
- Contract Version 全部为文本 4.0；
- 如果存在 EXPECTED_QUEUE_ID / EXPECTED_COUNT，必须分别等于 Queue ID / T。
不得读取 superseded、deferred 或 committed Queue 作为本次题组，不重新计算、不换题、不用非到期旧词补位。presented 只用于给同一个未提交场次补充新增 Position，绝不能重写已经存在的题。

若没有 active Queue，检查是否存在唯一 requested 素材缺口并按模式选择规则处理；否则明确报告“当前没有需要准备题目的 v4 当日题组”。若多于一个 active Queue，报告全部 Queue ID/Queue Date 并停止。

3. 确定本次 REQUIRED Position：先保留 Answer Drafts 中已经锁定或 submitted 的 Position，再按 Daily Queue 的 Position 从小到大补足到 T 个。读取 Session Questions。active 指 Question Status 为 staged、ready 或 bound，且 Queue ID / Contract Version 匹配。允许多个 Generation ID 作为内部暂存段，但必须满足：
- 每个 Generation ID 内 Position 无重复；所有 active Generation ID 合并后 Position 也无重复；
- 每行身份与 Daily Queue 同 Position 精确一致；
- bound 行必须保留原题、原答案和原 Session ID，绝不重写；
- active Position 必须属于 REQUIRED；Question Status=deferred 或 rejected 的历史行不属于本次题组，不读取其题目内容，也不得因此扩大 REQUIRED。若仍存在 REQUIRED 之外的 active 行，报告状态冲突并停止。
若 active Position 已完整覆盖 REQUIRED，固定范围回读后直接给出 Web App 链接，不重复生成。否则以 REQUIRED 中尚未覆盖的 Position 作为 MISSING；若存在重复或身份冲突，停止并报告歧义。staged/ready 的不完整合法段不是错误，不得覆盖或删除。

4. 出题前必须为 MISSING 中每个身份读取下列有界历史：Phrase Bank 的 Review Stage、Last Result、Common Mistake、Natural Example；Review Log / Error Log 中该 Phrase ID 最近错误及真实答案；Session Questions 中该 Phrase ID 或 Candidate ID 的全部历史题目，至少重点比较最近5题。不得只看 Daily Queue 当前行。

按记忆阶段选择正式题型：
- 新词、上次 forgotten、Review Stage 1–2：优先 cloze，只挖掉词块内部最关键的1个组成部分，作答范围标为“词块组成部分”；
- Review Stage 3–5：优先 cloze，要求回忆完整目标词块，作答范围标为“完整目标词块”；
- Review Stage 6–8：优先 recall / scenario / contrast / oral，从中文含义或短情境回忆完整目标词块，作答范围标为“完整目标词块”；
- 最近 Error Log 暴露出近义词混淆、介词、时态、搭配边界或漏词时，下一题必须定向检查该错误点，但不能泄露答案。

每道正式题的 Prompt ZH 开头必须且只能出现一个明确标签：`【作答范围：词块组成部分】` 或 `【作答范围：完整目标词块】`。标签之后只给完成作答所需的最短背景；不得出现一大段无法判断要不要翻译的背景，不得要求翻译整段或写完整英文句子。完整句写作属于正式题组之外的迁移挑战。

同一身份的语境必须轮换：禁止复用历史完整句；不得重复最近3题的核心场景；与最近1题相比，actor / domain / event / syntax 四项中至少改变两项。即使目标词块相同，也要让用户脱离旧场景线索独立回忆。

5. 本次只为 MISSING 中最靠前的 S 个 Position 生成题目，S=min(30, MISSING 数量)。这是 AI 内部稳定暂存段，不是新的用户题组；网页显示本次实际生效的 T 题，并最终只提交一次。每个选中身份各生成一道题：
- Position、Phrase ID、Candidate ID 与 Daily Queue 原样一一对应；
- Question Type 只能 recall、cloze、contrast、scenario、oral；
- 在符合上述阶段映射的前提下混合回忆、情境表达、辨析和口语，不连续堆叠同一题型；
- Prompt ZH / Prompt EN 至少一个非空，且不能直接出现目标 Chunk 或完整 Expected Answer；
- 若常见近义表达也成立，Semantic Boundary 必须明确区分；
- Expected Answers JSON、Accepted Variants JSON 均为非空 JSON 字符串数组；
- Grading Rubric 写清核心搭配、可接受变化和不能接受的边界；
- Candidate ID 非空且 Origin Type=user_context 时，读取其 Origin Context ID、Selected Text 和对应 Context Inbox Raw Text；首次学习优先利用真实语境，但不能泄露答案；
- 不在聊天中发送参考答案。

6. 使用新的唯一 Generation ID，例如 GEN-<Queue ID>-<yyyyMMddHHmmss>。向 Session Questions 一次性追加 S 行，每行严格 21 个 CellData，顺序为：
Queue Date | Queue ID | Position | Phrase ID | Candidate ID | Question Type | Prompt ZH | Prompt EN | Expected Answers JSON | Accepted Variants JSON | Semantic Boundary | Grading Rubric | Generation ID | Model ID | Prompt Version | Content Hash | Question Status | Session ID | Created At | Bound At | Contract Version

写入规则：Position 使用本段实际缺失 Position；Model ID 写当前实际模型；Prompt Version=english-review-v4-question-4；Content Hash 留空；Question Status=staged；Session ID/Bound At 留空（即使 Queue 已 presented，也由 Apps Script 绑定）；Created At 写真实 Asia/Shanghai 时间；Contract Version 写文本 4.0。

7. 固定范围回读确认：本次恰好 S 行、同一个新 Generation ID、Position 精确等于本段选中的缺失集合、身份与 Queue 逐行一致、每题恰好一个作答范围标签、没有历史原句复用、JSON 可解析且非空、状态全为 staged、Contract Version 全为文本 4.0；再回读该 Queue 的全部 active 行，确认无重复且覆盖数增加 S。

8. 成功后回复：
“题目暂存段已准备好。请返回答题网页检查完整题组；若仍有缺失，网页会继续提供下一段完整提示词：YOUR_WEB_APP_URL”
不要在聊天中直接展示题目，不要把 Queue 改为 presented。

====================
grading：按实际提交的答案集合批改
====================

1. 读取 Commit Journal，只筛选 Status=awaiting_chatgpt、Contract Version=4.0。若存在 EXPECTED_SUBMISSION_ID，只筛选该 Submission ID 并要求恰好一行；若不存在，则全局必须恰好命中一个 Submission ID。0 个则回复“当前没有等待批改的提交”，多于 1 个则报告全部 Submission ID 并停止。

2. 回读并联结冻结数据：
- Answer Drafts：该 Submission ID + Session ID、Submit Status=submitted、Answer Hash 与 Journal 一致的实际提交集合，共 A 行；
- Session Questions：该 Session ID 中与上述 Position 对应、Question Status=bound 的 A 行；
- Daily Queue：该 Session ID + Queue ID 中与上述 Position 对应、Queue Status=presented、Contract Version=4.0 的 A 行。

A 必须是 1–150。实际 Position 可以是不连续集合；三处的 Position 集合必须精确相同且无重复，Phrase ID/Candidate ID 逐题一致，Answer 非空，Answer Hash 一致。Daily Queue 中其余未提交 Position 不参与批改，不判错、不改 SRS。

3. 逐题批改，Result 只能：
- forgotten：没有回忆出目标表达或实质错误；
- difficult：方向接近但搭配、形式、边界或自然度明显有问题；
- normal：正确自然，满足语义边界；
- mastered：正确自然稳定，显示熟练掌握。

每题还要提供 Feedback ZH、Error Category（无错可空）、0–1 Confidence、Evidence、Expected Answer。Confidence<0.75 仍给最可能结果，Apps Script 只让用户确认这些低信心题。

同时读取 Phrase Bank 中对应 Phrase ID 的 Review Stage，并生成“正式题组之外”的加练计划：
- 每个 Result=forgotten 或 difficult 的正式错误必须恰好生成1道 reinforcement；不设置本场或每日总上限，一错一题；
- reinforcement 必须换一个与正式题不同的短场景，只要求填写完整目标词块，针对本次具体错误点；不得再生成 reinforcement 的 reinforcement；
- Result=mastered 且批改前 Review Stage>=6 时，生成1道 sentence_challenge，要求用户用目标词块写一个完整英文句子；其他正式结果不生成完整句挑战；
- 加练不改变正式 Result，不计入正式题数，不影响 SRS。

Extra Practice JSON 必须是 JSON 数组。每个对象严格包含：sourcePosition、practiceType（reinforcement 或 sentence_challenge）、promptZh、expectedAnswers（非空字符串数组）、acceptedVariants（字符串数组，可空）、referenceAnswer（非空）、contextSignature（非空且能说明新场景）。reinforcement 的 expectedAnswers/acceptedVariants 只放目标词块；sentence_challenge 的 referenceAnswer 放一条自然完整例句。

4. 读取 Grade Inbox 中该 Submission ID / Session ID / Answer Hash 的 active staged 行。允许多个 Grading Batch ID 作为内部暂存段，但所有 active Position 合并后必须无重复、身份与冻结答案一致且只能属于实际提交集合。若已完整覆盖全部 A 个 Position，固定范围回读后复用；否则计算 MISSING。重复或冲突时停止。本模式不生成候选素材：如果现有 active staged 行中尚未出现 Candidate Suggestions JSON，本次新段第一行必须精确写文本 []、其余行留空；如果已经出现一次，本次所有行都留空。Extra Practice JSON 必须在整个提交的 active 行中恰好出现一次：首次暂存段第一行写入覆盖全部 A 题的完整加练数组（允许 []），其余行全部留空；若 active 行已经出现一次，本次所有行留空。

5. 本次只批改 MISSING 中最靠前的 G 个 Position，G=min(30, MISSING 数量)。使用新的唯一 Grading Batch ID，例如 GRD-<Submission ID>-<yyyyMMddHHmmss>。向 Grade Inbox 一次性追加 G 行，每行严格 19 个 CellData，顺序为：
Submission ID | Session ID | Answer Hash | Position | Phrase ID | Candidate ID | Result | Feedback ZH | Error Category | Confidence | Evidence | Expected Answer | Grading Batch ID | Prompt Version | Grade Status | Created At | Candidate Suggestions JSON | Contract Version | Extra Practice JSON

写入规则：沿用同一 Submission ID、Session ID、Answer Hash；本段共享新的 Grading Batch ID；Position 使用本段实际缺失集合；Prompt Version=english-review-v4-grade-5；Grade Status=staged；Created At 写真实 Asia/Shanghai 时间；Contract Version 写文本 4.0。

rejected 旧行不算 active，可修正后使用新 Grading Batch ID。不得覆盖先前合法 staged 段。

6. 固定范围回读确认：本次恰好 G 行、Position 精确等于本段缺失集合、一个新的 Grading Batch ID、身份/hash 一致、Result/Confidence 合法、状态全为 staged、Contract Version 全为文本 4.0；再回读该提交的全部 active staged 行，确认无重复、覆盖数增加 G，Candidate Suggestions JSON 只出现一次并精确为 []，Extra Practice JSON 只出现一次、可解析，且每个 formal error 恰好对应1道 reinforcement、没有总量截断。

7. 成功后回复：
“批改暂存段已完成。请返回答题页面；全部已提交题目覆盖后，系统才会统一核验、写入并显示结果。若仍有缺失，网页会继续提供下一段完整提示词：YOUR_WEB_APP_URL”

不得在这里宣称数据库已写入或复习已完成；只有 Apps Script 精确回读后才能显示 committed。
